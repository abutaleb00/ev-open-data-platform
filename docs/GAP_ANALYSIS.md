# Current Development Gaps & Known Gotchas

This document is a snapshot from a full codebase review (backend routes/controllers/middleware, Prisma schema, frontend app/store/lib), updated after a remediation pass that fixed every Phase 0/1 item below. Fixed items are kept here (not deleted) so the reasoning survives — each note says what the bug was, what the fix does, and where to look if it regresses.

## Fixed: Cross-Tenant Security Gaps

1. **Partner PATCH endpoints now check ownership.** `openDataController.patchExternalLocation` / `patchExternalEvse` / `patchExternalConnector` (`PATCH /open-data/external/...`) each fetch the target record first and return `403` if `req.partnerCompanyId` doesn't match its owning company. Verified live: a company-3 API key can no longer patch a company-2 location; it still succeeds against its own.
2. **`operatorSyncController.syncOperatorData` no longer lets *any* valid key mutate *any* other tenant — cross-operator sync now requires an explicit, Super-Admin-granted "master key" flag.** The real-world integration contract for this endpoint turned out to be legitimate multi-operator syncing: a single trusted upstream aggregator pushes updates for many downstream operators it manages, resolved by `operator_reference_id`/name in the payload, auto-creating the operator's `Company` if it doesn't exist yet. The first version of this fix removed that capability entirely (scoping every key strictly to its own company), which broke real production usage — a live example payload targeting `operator_reference_id: 684C87AD2CF745756546345435435` ("MaanRishfa Ltd") using an API key that belonged to a *different* company ("Adam Street Ltd") surfaced this immediately.

   The corrected fix adds `ApiKey.isMaster` (schema migration, `db push`-applied to the dev DB): a **regular key** (`isMaster: false`, the default) behaves exactly like the first fix — strictly confined to `req.partnerCompanyId`, ignoring `operator_reference_id`/`operator.name` for resolution purposes. A **master/aggregator key** (`isMaster: true`, grantable only by `SUPER_ADMIN` via `PATCH /open-data/keys/:id`) restores the original cross-operator resolve-or-create behavior, with the underlying bugs still fixed: new companies are created with `status: 'ACTIVE'` (not the invalid `'APPROVED'`), an existing company found by reference is refused if `status === 'SUSPENDED'`, and the nested `ChargePoint`/`Connector` upsert lookups remain scoped to the resolved company/charge point (closing the `hardwareId`/`connectorUid` collision path that could reassign a device across tenants, independent of master/regular mode). Verified live: a master-flagged key can now sync into "MaanRishfa Ltd" using the exact real payload; a regular key given the identical payload lands its data under its *own* company instead, never touching "MaanRishfa Ltd"'s records.
3. **`companyController.getAllCompanies` (`GET /api/v1/companies`) is now tenant-scoped.** Non-super-admins get `where: { id: userCompanyId }` (their own single company); `SUPER_ADMIN` still gets everything. Verified live: a `COMPANY_ADMIN` token now receives exactly one company in the response.
4. **`locationController.updateLocation` / `deleteLocation` / `deleteLocationImage` now check ownership**, matching the pattern already used by `chargePointController`/`connectorController`/`tariffController`: fetch first, then `403` if `role !== 'SUPER_ADMIN' && record.companyId !== userCompanyId`. Verified live against a real cross-tenant location.
5. **`sessionController.startSession` / `stopSession` now check ownership** of the connector's parent location before mutating, and `stopSession` sanity-bounds the client-supplied `kwhConsumed` to `0–1000`. Verified live: starting a session on a foreign connector now returns `403`.
6. **`openDataController.ingestExternalData`'s upsert now re-asserts tenancy.** Before upserting a location/charge point by numeric ID or `hardwareId`, it checks whether an existing record with that ID already belongs to a different company and skips it (reporting `skippedIds` in the response) instead of silently overwriting it.
7. **`GET /open-data/feed?preview=true` no longer bypasses moderation.** The public feed always filters `isApproved: true` now; the `preview` query flag was removed from this unauthenticated endpoint. The equivalent authenticated, tenant-scoped preview remains available at `GET /open-data/preview/feed`.
8. **`GET /open-data/tariffs` now filters to `company.status: 'ACTIVE'`** so tariffs belonging to pending/suspended companies are no longer exposed on the public, unauthenticated feed.
9. **The dev-only `GET /api/v1/charge-points-test` route was removed** from `server.js` along with its now-unused `PrismaClient` import — it dumped every charge point, unauthenticated and unscoped.

## Fixed: Functional Bugs

- **`Company.status: 'APPROVED'` is gone.** It was never a recognized value anywhere else (`adminController`, `authMiddleware.protect`, `verifyPartnerApiKey` only ever check `PENDING`/`ACTIVE`/`SUSPENDED`), and would silently break a partner-synced company's subsequent auth/API-key checks. `syncOperatorData`'s master-key auto-provisioning path (see gap #2 above) now creates new companies with `status: 'ACTIVE'` instead. The pre-existing `MaanRishfa Ltd` company in the dev database (created by the old buggy code, `id: 2`) was manually corrected from `'APPROVED'` to `'ACTIVE'` via `PUT /admin/companies/2/status` during this fix pass, since it's the exact company the live example payload targets.
- **The moderation queue is now reachable.** `locationController.createLocation` and `chargePointController.createChargePoint` set `isApproved: role === 'SUPER_ADMIN'` — a Super Admin's own creates are still auto-approved (they are the moderator), but a `COMPANY_ADMIN`/`STAFF` submission now starts unapproved and shows up in `GET /admin/moderation/submissions` for review, verified live end-to-end (create → appears in queue → approve). The self-approval loophole was also closed: `updateLocation`/`updateChargePoint` now only honor an `isApproved` change in the request body when the caller is `SUPER_ADMIN`. Partner sync/ingest paths (`operatorSyncController`, `openDataController.ingestExternalData`) remain auto-approved by design — a valid, active partner API key is treated as sufficient trust.
- **`publicApiController.getPublicDataset` now selects `media`** so `loc.media` resolves instead of always being `undefined` — the `images` field in this legacy endpoint's response is no longer permanently `[]`.
- **`moderationController.getMainMaintenanceSettings` now uses `findFirst()`** instead of a hardcoded `id: 1`, matching every other `SystemConfig` consumer and removing the config-drift risk if the singleton row's ID is ever not `1`.
- **Partner API keys are no longer stored as plaintext.** `ApiKey.key` stores an HMAC-SHA256 hash (`backend/src/utils/apiKeyHash.js`, keyed by `API_KEY_PEPPER` or `JWT_SECRET`), used only for the fast auth lookup in `verifyPartnerApiKey`. **This is a breaking change for any already-issued API key** — existing plaintext keys stored before this fix will no longer authenticate, since the stored value no longer matches a hash of itself. All partner integrations need a freshly generated key after this deploy.
  - **Follow-up product decision, superseding the initial "shown once, never again" design**: the first version of this fix made `GET /open-data/keys` strip the key value entirely (matching the GitHub/Stripe/AWS "shown once at creation" pattern). The user explicitly asked for persistent recoverability instead — a Super Admin or the owning company needs to be able to copy a key's value again anytime, not just at creation. `ApiKey` now also stores `encryptedKey` (AES-256-GCM, reversible), and `GET /open-data/keys` decrypts and returns the real value for every key created after this change. **This is a deliberate security tradeoff, not an oversight**: a database compromise can now recover every live API key (a hash-only design couldn't), so `API_KEY_PEPPER` must be treated as sensitive as `JWT_SECRET` and kept out of source control. Keys created before `encryptedKey` existed have no recoverable value (only their hash was ever stored) — the API returns `key: null` for those, and the frontend (`open-data/keys/page.jsx`) shows "not recoverable, revoke and regenerate" instead of a masked/copyable value.
- **`DELETE /open-data/keys/:id` (revoke) now exists.** The frontend's "Revoke" button previously called a route that didn't exist anywhere in the backend and always failed. `openDataController.revokeApiKey` now tenant-checks and flips `isActive: false` (soft revoke, preserving the audit trail); `verifyPartnerApiKey` already rejected inactive keys, so revocation is immediately effective. Verified live: sync-operator call with a freshly revoked key now returns `403`.

## Fixed: Secret / Sensitive-Data Handling

- **`authController.js` no longer hardcodes SMTP fallback credentials.** If `MAIL_HOST`/`MAIL_USER`/`MAIL_PASS` aren't set, `sendVerificationEmail` now logs a warning and skips sending instead of attempting a connection with a real third-party mailbox's credentials baked into source. The `FRONTEND_URL` fallback was also changed from a specific external production domain to `http://localhost:3000`, and the "from" address / support-contact link in the email template now derive from `MAIL_USER`/`SYSTEM_EMAIL_FROM` instead of a hardcoded foreign address.
- **`operatorSyncController`'s raw error leak is gone** — the rewrite (see gap #2) no longer returns `error: error.message` to the client; it logs server-side only, matching every other controller.
- **`prisma/seed.js` now supports `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` overrides**, with the previous hardcoded values kept only as local-dev fallbacks (documented as such in the file).

## Fixed: Frontend

- **The frontend's own developer-key listing pages no longer crash.** As a direct consequence of hashing API keys server-side, `developer-keys/page.jsx` and `open-data/keys/page.jsx` previously did `item.key.slice(0, 12)` on a value that is now always `undefined` — a hard `TypeError` on every render once a single key existed. Both pages now show a fixed masked placeholder for listed keys and surface the real one-time secret only in the creation-success modal, with a copy button there instead of per-row.
- **Hardcoded API base URLs replaced with `NEXT_PUBLIC_API_URL`** in `src/lib/axios.js`, `src/components/landing/Hero.jsx`, `src/components/landing/Footer.jsx` (previously pointed at two different domains from each other), and `src/app/(public)/register/page.jsx` (which also now goes through the shared `api` Axios instance instead of a raw `axios.post` call with its own duplicated fallback).

## Corrected: `src/proxy.js` is not dead/misnamed code

An earlier version of this document (and this project's own analysis, before this fix pass) claimed `src/proxy.js` was dead code because of a wrong filename/export — that claim was based on outdated Next.js knowledge and was **incorrect**. This project runs Next.js 16, which renamed `middleware.js`/`export function middleware` to `proxy.js`/`export function proxy` (confirmed against `node_modules/next/dist/docs`). The file is written correctly per that convention: right path (`src/proxy.js`, alongside `app`), right export name, right `config.matcher`.

It is still **inert in this deployment**, but for a different, verified reason: `next.config.mjs` sets `output: 'export'`, and Next.js does not support Proxy/Middleware in static export mode at all — `next build` prints `⚠ Statically exporting a Next.js application via 'next export' disables API routes and middleware` and the exported static bundle never invokes it at request time (confirmed by an actual local build). The real, enforced route protection is the client-side redirect in `src/app/(dashboard)/layout.jsx` plus backend API authorization on every data-fetching call — this was already true before the fix pass and remains true now. The file was left in place with a clarifying comment rather than rewritten, since the code itself isn't broken; if the deployment target ever moves off static export, it starts working exactly as written.

## Still Open (see `docs/ROADMAP.md` for prioritization)

- **Rate limiting is still in-memory and per-process** (`globalRateLimiter` in `server.js`, `feedRateLimiter`'s cached config in `requestTracker.js`). Horizontal scaling still breaks the intended global limits. Not changed in this pass — needs `rate-limit-redis` (Phase 2 in the roadmap).
- **Response-shape inconsistencies remain** (`authController.login`'s top-level `token`/`user`, `dashboardController.getDashboardMetrics`'s top-level `role`/`summary`/`chartData`, three different pagination `meta` shapes across `auditController`/`openDataController`/`trafficController`). Not changed in this pass — these are call-signature changes that need frontend updates in lockstep, deferred to avoid scope creep on a security-focused pass.
- **`trafficController.js`, `maintenanceInterceptor.checkPortalGate`, and `rateLimiter.js`'s `publicFeedLimiter` are still orphaned/dead code.** Harmless (nothing routes to them), left in place rather than deleted in this pass.
- **`dashboardController.getDashboardMetrics` still aggregates in JavaScript** rather than via DB-side `groupBy`/aggregate queries. Not a correctness bug, but a scale concern deferred to the roadmap.
- **No automated test suite exists** for either backend or frontend. All fixes in this pass were verified with live manual integration tests against the real dev database (documented inline above) rather than an automated suite, since none exists yet to extend.
